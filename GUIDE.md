# Справочник: куда лезть, чтобы что-то поменять

Шпаргалка по проекту. Слева — что вы хотите сделать, справа — какой файл открыть.

Номера строк указаны на момент написания и со временем поедут — ориентируйтесь
на комментарии-разделители вида `/* ---------- шапка ---------- */`, они есть
и в CSS, и в JS. Поиск по такому комментарию всегда приведёт куда нужно.

**Важно, что изменилось с первой версии:** виды работ, их поля и разделы прайса
больше НЕ в коде — они в базе и настраиваются администратором в интерфейсе.
В `seed_catalog.py` лежит только стартовый набор для первого запуска.

**Фронтенд переехал на React.** Прежний `static/js/app.js` на 3600 строк
разбит на компоненты в `web/src`. Что это меняет на практике:

- разметка лежит рядом с логикой конкретного экрана, а не в одной большой
  шаблонной строке — искать нужно по названию папки в `features/`;
- поля формы и состояние окон хранит сам React, вручную собирать значения из
  DOM (`collectForm`, `collectWork`) больше не нужно;
- после изменения данных не нужно звать перерисовку руками: список
  обновляется сам, потому что сброшен соответствующий ключ кэша (`api/keys.ts`);
- **классы CSS остались прежними** — `static/css/app.css` не тронут, вся
  таблица «где стиль какого элемента» ниже по-прежнему верна.

Сборка: `cd web && npm run build`. Результат кладётся в `static/dist`, его и
отдаёт сервер. Пока новый интерфейс обкатывается, старый доступен на `/legacy`.

### Как открыть окно

```tsx
const modal = useModal();
modal.open(<ЧтоТо />);                                  // вместо всего
modal.push(<ЧтоТо />, { backLabel: '← К заказу' });      // поверх, с возвратом
modal.replace(<ЧтоТо />);                                // заменить текущее
```

Окна складываются стопкой и **остаются живыми под верхним**. Поэтому из
наполовину заполненной формы заказа можно заглянуть в карточку клиента и
вернуться — введённое на месте. Сохранять черновик руками не нужно.

## Частые задачи

### Поменять текст на кнопке или подпись поля
Поиском по `web/src`. Текст лежит прямо в разметке компонента.

### Добавить поле в форму заказа
Речь про поле самого заказа, а не про поле вида работ (те настраиваются
через интерфейс). Нужны пять правок:

1. `web/src/types/api.ts` — поле в `Order` и в `OrderCreatePayload`;
2. `web/src/features/orders/OrderFormModal.tsx` — в `FormState`,
   в `initialState()`, в `buildPayload()` и сама разметка:
   ```tsx
   <Field label="Подпись">
     <input type="text" value={form.поле} onChange={(e) => set('поле', e.target.value)} />
   </Field>
   ```
3. `app/schemas.py` — классы `OrderBase` и `OrderUpdate`;
4. `app/models.py` — колонка;
5. `app/database.py` — та же колонка в `ADDED_COLUMNS`, иначе на существующей
   базе будет «no such column».

Компилятор подскажет, если забыли шаг 1 или 2: `npm run check` в папке `web`.

### Добавить новый вид работ или раздел прайса
**Через интерфейс**, кодом ничего делать не нужно: разделы «Виды работ» и
«Прайс» под администратором. Раздел прайса и позицию можно создать прямо из
конструктора поля.

### Добавить новый способ расчёта (роль поля)
Это единственное, что требует кода. Четыре места:
1. `app/pricing.py` — обработка роли в `estimate_from_fields()` и описание в шапке файла;
2. `app/catalog.py` — ключ в `PRICING_ROLES`;
3. `web/src/types/api.ts` — ключ в типе `PricingRole`;
4. `web/src/features/works/fieldKinds.ts` — `MONEY_ROLES` (как считать),
   `ROLE_UNITS` (какие единицы прайса ей подходят), при необходимости
   `SIZE_REQUIREMENTS` (нужны ли размеры) и `FIELD_KINDS` (новый вид поля).

### Поменять формулу расчёта
`app/pricing.py`, функция `estimate_from_fields()`. Цифр там нет — они в базе.
В коде только логика: что на что умножить.

### Поправить поиск превью в CDR
`app/cdr.py`. Порядок попыток: zip-архив (X4+), контейнер RIFF (X3 и старше),
сканирование байтов. Если ваша версия CorelDRAW кладёт эскиз по другому пути,
посмотрите `GET /api/orders/{id}/design/inspect` — там список вложений — и
допишите подсказку в `THUMB_HINTS`.

### Поменять вид блока макета
`web/src/features/design/DesignBlock.tsx`, увеличение превью —
`design/Lightbox.tsx`. Стили — раздел `макеты` в `app.css`, классы `.dz-*`.

### Добавить иконку для вида работ
Три места: сама иконка в `web/src/components/Icons.tsx` (компонент плюс
запись в словаре `BY_NAME`), список `ICONS` в
`web/src/features/works/WorkEditorModal.tsx` и список `ICONS` в
`app/routers/templates.py` — сервер принимает только известные ему имена.

### Добавить или переименовать статус заказа
`app/models.py`: `OrderStatus` (сам статус), `STATUS_META` (название, подсказка,
цвет колонки), `ALLOWED_TRANSITIONS` (откуда куда можно двигать), `FORWARD`
(куда ведёт стрелка на карточке). Доска подхватит автоматически.

### Поменять формат номера заказа
`app/routers/orders.py`, функция `next_number()` — там префикс `ЗК` и
разрядность `:06d`.

### Добавить новое право доступа
1. `app/permissions.py` — дописать словарь в `PERMISSIONS` (ключ, название,
   подсказка, раздел). Страница «Сотрудники» подхватит автоматически.
2. На сервере: `Depends(require_perm("ваш.ключ"))` в нужной ручке.
3. `web/src/types/api.ts` — ключ в тип `Permission`.
4. На фронтенде: обернуть элемент в `can('ваш.ключ')`.

Шаг 3 нужен, чтобы опечатку поймал компилятор: `can('orders.pirce.view')`
раньше просто прятал кнопку навсегда и находился на живом заказе.

Шаг 2 обязателен — прятать только в интерфейсе бесполезно, сотрудник откроет
адрес API напрямую. Если право закрывает данные внутри ответа (как цены),
фильтровать нужно в `to_out()` соответствующего роутера.

### Поменять порядок заказов в колонках
`web/src/features/board/sorting.ts` — объект `SORTERS` со всеми режимами.
Новый режим: добавить функцию туда, ключ в тип `BoardSort`
(`web/src/app/Shell.tsx`) и строку в `SORT_OPTIONS`
(`web/src/features/board/BoardFilters.tsx`).

### Добавить новый раздел (вкладку в шапке)
`web/src/app/views.ts` — адрес, подпись, иконка и право. Дальше маршрут в
`web/src/app/Shell.tsx` и сама страница в `web/src/features/…`.
Навигация и защита по правам строятся по этому списку сами.

---

### Добавить колонку в таблицу
1. `app/models.py` — поле в модели;
2. `app/database.py` — та же колонка в словарь `ADDED_COLUMNS`, иначе на
   существующей базе будет «no such column»;
3. если колонка приходит с клиента — `app/schemas.py` или схема в роутере.

Перед изменением схемы система сама снимет копию базы в `backups/..._before-update`.

## Как проверять правки

Два окна терминала, и правки видно сразу:

```bash
uvicorn app.main:app --reload      # окно 1: сервер и API
cd web && npm run dev              # окно 2: интерфейс на http://localhost:5173
```

Открывать при разработке нужно **http://localhost:5173** — там страница
обновляется сама, без перезагрузки и без потери того, что вы ввели в форму.
Запросы к `/api` уходят на uvicorn, настраивать ничего не надо.

Порт 8000 отдаёт последнюю **собранную** версию. Чтобы обновить её:

```bash
cd web && npm run build
```

Дальше:

1. `npm run check` в папке `web` — проверка типов без сборки. Быстрее, чем
   ловить ошибку в браузере: опечатки в именах полей API она ловит сразу.
2. F12 → Console: красные ошибки. В режиме `npm run dev` React показывает
   и номер строки в исходнике.
3. F12 → Network: какой ответ вернул сервер (200 — всё хорошо, 401 — нужен
   вход, 403 — не хватает прав, 422 — сервер не принял данные, 500 — ошибка,
   её текст будет в консоли uvicorn).
4. `python -m scripts.check_db` — целостность базы, счётчики записей, возраст
   бэкапа. И `python -m scripts.backup` перед любой рискованной правкой.

Если новый интерфейс совсем не открывается, старый лежит на `/legacy` —
им можно работать, пока разбираетесь.

## Чего лучше не трогать без нужды

- `app/security.py` — подпись токенов. Ошибка здесь тихо откроет доступ.
- `_ensure_columns()` и `check_integrity()` в `app/database.py` — обновление
  схемы на живой базе и проверка на повреждение. Если сломать, при следующем
  обновлении получите «no such column» или незамеченную порчу данных.
- Ключи полей видов работ (`TemplateField.key`) — под ними лежат значения в
  уже созданных заказах. Переименование ключа осиротит данные во всех заказах
  этого вида. Подпись менять можно свободно, ключ — нет.
- Функцию `esc()` в `app.js` — она экранирует пользовательский текст. Если
  вставлять данные в HTML мимо неё, имя клиента с угловой скобкой сломает
  вёрстку, а в худшем случае даст выполнить чужой скрипт.
- `if_version` и подобные проверки в API — они защищают от одновременной
  правки одного заказа двумя людьми.

## Полезное про CSS в этом проекте

- Никаких фреймворков и сборки — обычный CSS, правки видны сразу после Ctrl+F5.
- Отступы и размеры почти везде в пикселях, шрифты — тоже. Это сделано
  намеренно: предсказуемо и легко править.
- Анимации завязаны на `--ease`, длительность обычно `.15s`–`.22s`.
  Если хотите убрать все анимации — ищите `transition` и `animation`.
- Атрибут `hidden` в этом проекте всегда прячет элемент: в начале CSS стоит
  `[hidden]{display:none !important}`. Показать элемент из JS —
  `el.hidden = false`.
- Экранирование `${}` внутри шаблонных строк JS: если нужен доллар с фигурной
  скобкой буквально — ставьте `\${`.

# ПОСТЕР · система заказов

Внутренняя канбан-доска для сотрудников: приняли заказ → подтвердили → сделали → выдали.
Бэкенд на FastAPI, база локальная (SQLite), фронтенд — React + TypeScript
в стиле сайта ПОСТЕР.

## Запуск

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env               # и задайте пароль администратора

python -m scripts.seed_demo        # необязательно: 13 демо-заказов по всем статусам
uvicorn app.main:app --reload
```

- Интерфейс — http://127.0.0.1:8000/
- Документация API (Swagger) — http://127.0.0.1:8000/docs

База создаётся сама в файле `poster.db` рядом с проектом. Если она пустая —
при первом запуске в неё заливается стартовый каталог: семь видов работ,
16 разделов прайса с подразделами и цены. На базе, где уже что-то есть, это не срабатывает
никогда — удалённый раздел не вернётся сам.

### Фронтенд

Собранный интерфейс лежит в `static/dist` и отдаётся сервером — для обычного
запуска ничего делать не нужно. Пересобрать после правки исходников:

```bash
cd web
npm install       # только в первый раз
npm run build
```

Для разработки удобнее режим с горячей перезагрузкой: страница обновляется
на лету, не теряя того, что введено в форму.

```bash
cd web && npm run dev     # http://localhost:5173, запросы к /api идут на :8000
```

Проверить типы, не собирая: `npm run check`.

После пересборки страницу не нужно обновлять «с силой»: сервер отдаёт
`index.html` с `Cache-Control: no-cache`, поэтому новые файлы сборки браузер
подхватывает сам. Сами файлы сборки кэшируются как обычно — в их именах хэш.

Нужен Node.js 20 или новее. Прежний интерфейс на ванильном JS оставлен
запасным вариантом и доступен на `/legacy` — его можно удалить вместе с
`static/index.html` и `static/js/`, когда новый отработает на живых заказах.

## Переезд на серверную базу

Ничего в коде менять не нужно — только переменную окружения:

```bash
export POSTER_DB_URL="postgresql+psycopg://user:pass@host:5432/poster"
pip install "psycopg[binary]"
```

Таблицы создаются через `Base.metadata.create_all` при старте. Когда схема начнёт
меняться на живых данных, стоит подключить Alembic — сейчас это лишнее.

## Тесты

```bash
pip install -r requirements-dev.txt
pytest
```

Базу тесты не трогают: расчёт цены — чистая функция от словарей, весь прогон
занимает секунду. Проверяются три вещи, ошибка в которых не падает, а тихо
портит данные:

- **расчёт цены** по каждой роли поля, включая случаи, на которых система уже
  спотыкалась (снятая галочка, удалённая позиция прайса, ноль в счётчике);
- **платёжная строка для QR** — состав полей, копейки в `Sum`, вычистка
  разделителей из названий, проверка реквизитов;
- **переходы статусов** — что кнопка «дальше» не предлагает запрещённого
  и что до «Выдан» можно дойти, не перепрыгивая этапы;
- **сверка правила про размеры** между `app/pricing.py` и его копией в
  `web/src/features/orders/dimensions.ts` — на всех 48 сочетаниях выбора.
  Для этой проверки нужен Node.js; если его нет, тест пропускается.

Расхождение копий — тупик для сотрудника: форма гасит поле как ненужное,
а сервер отказывается считать без него. Поэтому сверяется машинно.

В Windows-консоли имена тестов написаны по-русски и могут выводиться
крякозябрами — лечится `set PYTHONIOENCODING=utf-8` перед запуском.

## Профили и права

При первом заходе открывается экран выбора профиля — плитки с именами
сотрудников плюс «Администратор».

- **Администратор** — пароль из `.env` (`POSTER_ADMIN_PASSWORD`). Всегда имеет
  все права. Это же способ восстановить доступ, если профили удалили или
  забыли пароли.
- **Сотрудники** — профили, которые администратор создаёт в разделе
  «Сотрудники»: имя, набор прав, список компьютеров и необязательный пароль.

### Привязка к компьютеру

У профиля два режима доступа:

- **С любого компьютера** — как раньше, профиль виден везде.
- **Только с выбранных** — профиль появится в списке входа лишь на указанных
  рабочих местах. На остальных он показан серым с пометкой «другой компьютер».

Компьютеры появляются в разделе «Сотрудники → Устройства» сами, как только с
них открыли систему. Администратор даёт им имена («Приёмка», «Ноутбук в цехе»)
и отмечает в профиле нужные.

Привязка проверяется на каждом запросе, а не только при входе, — скопированный
на другую машину токен не сработает.

**Как это устроено и чего не умеет.** Браузер не может прочитать MAC-адрес,
серийник диска или другой идентификатор оборудования — таких API не
существует ни в одном браузере. Поэтому компьютер опознаётся по случайному
ключу, который браузер генерирует один раз и хранит у себя. Отсюда следствия:

* очистка данных сайта, режим инкогнито или другой браузер на том же
  компьютере = новое устройство, привязку нужно обновить;
* человек с доступом к консоли браузера может скопировать ключ на другую
  машину.

То есть это защита от «зашёл под своим профилем из дома или с чужого рабочего
места», а не от целенаправленного обхода изнутри. Для внутренней системы в
офисе этого достаточно; если понадобится строже — следующий шаг это HTTPS с
клиентскими сертификатами либо вход через доменные учётные записи.

Пароль можно задать дополнительно к привязке — например, если за одним
компьютером работают посменно разные люди.

Администратор входит с любого компьютера всегда: это способ восстановить
доступ, если привязки настроены неверно.

### Права

Настраиваются галочками по разделам, есть быстрые наборы: «Приёмщик»,
«Производство», «Старший смены». Полный список — в `app/permissions.py`.

Что можно закрыть: доску заказов, создание, редактирование, смену статуса,
удаление, **стоимость каждого заказа**, расчёт по прайсу, суммы по колонкам,
контакты клиентов, поиск по базе клиентов, историю клиента, метрики, просмотр
и правку прайса, управление сотрудниками.

Права проверяются **на сервере**, а не только прячутся в интерфейсе. Если у
сотрудника нет права `orders.price.view`, цены не придут в его браузер вообще —
открыть `/api/orders` напрямую и увидеть их не получится. Изменение прав
действует сразу: сотруднику достаточно обновить страницу, перезаходить не надо.
Отключение профиля мгновенно закрывает доступ.

Пароли хранятся хешем (PBKDF2). Посмотреть чужой пароль нельзя — только задать
новый.

Подбор пароля упирается в счётчик: после пяти неудачных попыток вход в этот
профиль с этого компьютера закрывается на минуту. Счётчик живёт в памяти
процесса — перезапуск сервера его обнуляет, задача была сделать перебор
медленным, а не пережить перезагрузку.

Кто может обращаться к API из браузера, задаёт `POSTER_ALLOWED_ORIGINS`
в `.env`. По умолчанию разрешены только сам сервер и режим разработки —
интерфейс, открытый с этого же адреса, работает всегда.

Честно о границах: это разграничение внутри доверенного контура — защита от
«не своего дела» и случайностей, а не от целенаправленного взлома. Трафик
внутри сети не шифруется, пока не поставите HTTPS.

## Метрики

Раздел «Метрики» в шапке, периоды: неделя, месяц, квартал, год, всё время.

- заработано за период (по дате выдачи заказа), выдано заказов, средний чек;
- средний срок от создания до выдачи;
- график выручки по дням (по месяцам для периодов больше квартала);
- сейчас в работе и на какую сумму, сколько ждём доплаты;
- просрочено и сдать сегодня, заказы без указанной цены;
- разбивка по видам работ и клиенты по выручке;
- создано и отменено за период, доля отмен, предоплаты в кассе.

Выручка считается по моменту перехода заказа в «Выдан» — для этого у заказа
есть поле `completed_at`. Если вернуть заказ из «Выдан» назад, отметка снимается.

## Бэкапы

```bash
python -m scripts.backup              # полный бэкап: снимок файла + JSON по разделам
python -m scripts.backup --keep 30    # и удалить всё старше 30 последних
python -m scripts.backup --list       # что уже сохранено
```

Кладётся в папку `backups/` — она в `.gitignore`, там данные клиентов.
Каждый бэкап содержит снимок `poster.db` целиком плюс три файла JSON:
`orders.json` (с историей), `clients.json`, `prices.json`.

Снимок снимается штатным механизмом SQLite, поэтому останавливать сервер не нужно —
и он дотягивает незаписанные изменения из журнала WAL.

Отдельно, без запроса, копия снимается перед изменением схемы базы: такие папки
называются `..._before-update`.

Восстановление — по разделам, чтобы можно было вернуть прайс, не трогая заказы:

```bash
python -m scripts.restore --list                 # доступные бэкапы
python -m scripts.restore prices                 # вернуть прайс из последнего
python -m scripts.restore orders clients prices  # всё сразу
python -m scripts.restore prices --from 2026-08-02_14-30-05
python -m scripts.restore prices --mode replace  # стереть текущий раздел и залить из бэкапа
```

По умолчанию режим `merge`: существующие записи обновляются, новые добавляются,
лишнее в базе остаётся. Записи сопоставляются по естественным ключам (номер
заказа, телефон клиента, ключ позиции прайса), поэтому дубли не плодятся.

Если база потеряна целиком — проще остановить сервер и скопировать `poster.db`
из папки бэкапа на место рабочего файла.

## Печать

Кнопка «Печать» в карточке заказа. Два документа на выбор:

- **Квитанция клиенту** — шапка мастерской, номер заказа, состав, стоимость,
  внесено и крупно «к доплате», срок выдачи, место для подписи приёмки.
  У отменённого заказа вместо «приходите забирать» печатается отметка
  «Заказ отменён».
- **Наряд в цех** — номер и срок крупно, имя клиента, все параметры с
  единицами, файл макета, место для отметок «сделано / проверено / выдано».
  **Цен в наряде нет** — они закрыты правом `orders.price.view`, и печать не
  должна быть обходом этого правила. Квитанция по той же причине доступна
  только тому, у кого это право есть.

То, что видно в окне, и уходит на бумагу — отдельного предпросмотра нет.
Размер листа и поля выбираются в окне печати браузера; квитанция рассчитана
на A5, наряд — на A4.

Шапка квитанции — название, телефон, адрес, строка под ними и логотип —
задаётся в разделе **«Настройки»** (право `staff.manage`). Там же живут
платёжные реквизиты для QR. Значение, сохранённое в настройках, главнее
`.env`; в `.env` их можно оставить как запасной вариант для установки.

Размер листа выбирается прямо в окне печати: квитанции по умолчанию на A5,
наряды на A4, выбор запоминается на этом компьютере. Галочка «Две на листе»
печатает две одинаковые квитанции рядом на A4 поперёк (каждой — половина,
то есть A5) с пунктиром для разреза — приёмке и клиенту.

### Бирка на заказ

Третий документ в окне печати — **бирка** 90 × 55 мм на рулон или пачку:
номер заказа крупно (по нему ищут на полке), клиент и телефон, что внутри,
тираж, срок и кто принял. Цен на бирке нет. Переключатель «Штук» печатает
до восьми одинаковых бирок разом плиткой — по одной на каждый рулон; на A4
помещаются восемь (2 × 4), на A5 три в столбик. Режется по пунктиру.

## Сегодня и загрузка цеха

Над доской — полоса «Сегодня»: сколько заказов просрочено, сколько сдать
сегодня и сколько лежит готовых и ждёт клиента. Нажатие на счётчик оставляет
на доске только эти заказы, повторное — снимает отбор. Считается по всем
заказам, а не по отфильтрованным: срочность — про цех целиком.

Кнопка «Загрузка цеха» раскрывает неделю по дням: сколько заказов и сколько
квадратных метров печати приходится на каждый день по сроку сдачи, плюс
«просрочено», «позже» и «без срока». Площадь берётся из размеров в заказе
по тому же правилу, что и цена (первая ширина × первая высота × тираж), и
только у видов работ, где есть позиция «за м²»; остальное считается штуками.
Нужно приёмке: если на завтра уже 40 м² баннера, новый заказ честнее обещать
на послезавтра.

## Почта

Раздел «Почта» читает рабочий ящик по IMAP и отвечает с него по SMTP.
Право **«Работать с почтой»** (`mail.access`) включено по умолчанию: ящик
общий, отвечать клиентам — часть работы приёмки. Личные ящики сюда не
подключают — пароль хранится на сервере.

**Как подключить Яндекс.** В настройках ящика включите IMAP (Почта →
Настройки → Почтовые программы → «С сервера imap.yandex.ru по протоколу
IMAP»). Затем выпустите пароль приложения: id.yandex.ru → Безопасность →
Пароли приложений → Почта. Нужна двухфакторная защита аккаунта, без неё
Яндекс пароли приложений не выдаёт. Адрес ящика и этот пароль впишите в
«Настройки → Почта — рабочий ящик» и нажмите «Проверить соединение».
Другие почты работают так же — укажите свои серверы IMAP и SMTP.

**Что умеет.** Список писем подгружается частями по 30 при прокрутке и
держит в памяти не больше девяноста строк: ящик с тысячами писем листается
без тормозов. Открытое письмо отмечается прочитанным. Письма с оформлением
показываются как есть, с картинками, но в изолированной рамке без
скриптов; разметка вычищается на сервере по белому списку (ссылки только
http/https/mailto, картинки только https и вложенные), так что чужой код
на нашей странице не выполняется. Кнопка «Показать только текст» — на
случай, если оформление мешает.
Вложения скачиваются по нажатию. «Ответить» шлёт письмо с рабочего ящика
с подписью (имя сотрудника, название мастерской) и цитатой оригинала,
нить сохраняется. «Написать» — новое письмо. О новых письмах всплывает
уведомление, на иконке раздела — число непрочитанных.

**Как устроено.** Одно IMAP-соединение на сервер, список UID кэшируется
20 секунд, заголовки писем — навсегда (они не меняются), флаги
«прочитано» берутся свежими. Опрос «что нового» раз в 30 секунд с каждого
рабочего места упирается в серверный кэш на 20 секунд, так что ящик не
страдает от числа сотрудников.

## Уведомления о новых заказах

Право **«Получать уведомления о новых заказах»** (`notify.orders`),
по умолчанию выключено. У кого включено — при заказе, оформленном
кем-то другим, справа сверху всплывает окно: номер, работа, клиент, срок
и сумма (если её можно видеть), кнопки «Открыть» и «Скрыть». Висит
15 секунд, под курсором не исчезает. Со звуком — коротким сигналом;
браузер разрешает звук после первого нажатия на странице. Звук
выключается в профиле, там же кнопка «Проверить» и разрешение на
системные уведомления браузера — они показываются, когда вкладка
свёрнута.

Как это устроено: браузер раз в 12 секунд спрашивает
`GET /api/orders/fresh?after=<id>` — что появилось после последнего
виденного заказа. Свои заказы не приходят. Планшет в цехе с погашенной
вкладкой тоже получает сигнал: опрос идёт и в фоне.

## Касса за день

Нажатие на счётчик «в работе» в шапке (право `finance.totals`) открывает
кассу за день: сколько принято наличными и переводом, что вернули, итог,
разбивка по сотрудникам и список движений с переходом в заказ. Стрелки и
поле даты листают дни назад.

Откуда берутся строки. Заказ по-прежнему хранит только итог «внесено», а
каждое его изменение оставляет запись в журнале движений (таблица
`payments`, логика в `app/ledger.py`): разница между тем, что было на руках,
и тем, что стало. Доплата — плюс, возврат или уменьшение внесённого — минус.
Когда внесённое меняется, форма заказа спрашивает, как приняли деньги:
наличными или переводом; последний выбор запоминается на этом компьютере.
Заказы, оформленные до появления журнала, в кассе не видны — по ним есть
только итог в карточке.

Ручка: `GET /api/reports/cash?from=…&to=…` — границы местных суток в ISO
считает браузер, серверу часовой пояс стойки неизвестен.

## Профиль и рабочее место

Нажатие на имя в шапке открывает страницу профиля: кто вошёл, с какого
устройства, что разрешено (человеческими словами, по справочнику прав),
быстрые клавиши, кнопки «Сменить профиль», «Касса за день», «Перечитать
данные».

Там же настройка **автообновления доски** — она личная для этого браузера
и профиля, хранится в нём, а не на сервере. Планшету в цехе включают
«каждые 30 секунд» или «каждую минуту»: новые заказы появляются, даже
если экран никто не трогает. За стойкой обычно не нужно: доска и так
перечитывается при возврате в окно и после каждого сохранения. В свёрнутой
вкладке опроса нет.

## Касса за день

Открывается нажатием на счётчик «в работе» в шапке или со страницы
профиля. Нужно право **«Сверять кассу»** (`finance.cash`) — оно отдельное
от «видеть суммы по колонкам»: суммы в работе видят несколько человек,
а ящик вечером сверяет один. Администратору доступно всегда.

В окне: итоги наличными и переводом, по сотрудникам, список движений с
переходом в заказ, листание дней. Кнопка «Печать» выводит итог дня на
A4 (заголовок с датой и временем печати), «CSV» выгружает движения
файлом для Excel (время в файле — UTC, как в базе).

## Резервные копии

Раздел «Журнал» показывает, когда была последняя копия, и краснеет, если
она старше суток или её не было вовсе. Кнопка «Сделать копию сейчас»
делает то же, что скрипт: снимок файла базы штатным механизмом SQLite
(безопасно на живом сервере) и выгрузку в JSON по разделам в
`backups/<дата_время>/`.

Раз в сутки копию должен делать планировщик Windows — команда в шапке
`scripts/backup.py`:

```bat
schtasks /Create /SC DAILY /ST 03:00 /TN "ПОСТЕР бэкап" /TR "\"D:\poster\.venv\Scripts\python.exe\" -m scripts.backup --keep 30" /RU SYSTEM
```

Пути подставьте свои; задача должна запускаться из корня проекта.
Восстановление — `python -m scripts.restore --help`.

## Клиенты

Карточки заводятся сами при создании заказа. Имя и телефон в заказе — снимок
на момент сделки: карточка из заказа только дополняется, а правится в самой
карточке. Указали в заказе другой номер — заказ привяжется к карточке с этим
номером или заведёт новую, прежнюю не тронет.

**Дубли** сливаются кнопкой «Объединить…» в карточке: заказы переезжают в
выбранную, её пустые поля дополняются, исходная удаляется. Отменить нельзя,
поэтому вопрос перед этим подробный.

Сумма в карточке и в списке — без отменённых и без возвратов: та же мерка,
что в метриках.

## Выгрузка в CSV

«Выгрузить CSV» на метриках (заказы за выбранный период) и в клиентах (весь
справочник). Формат под Excel по-русски: `;`, десятичная запятая, BOM.
Деньги и контакты попадают в файл только при наличии прав на них.

## Журнал

Раздел «Журнал» в шапке — для тех, у кого есть право управлять сотрудниками.
Последние строки лога, выбор файла, «только проблемы». Внутренняя ошибка
показывает сотруднику короткий номер — по нему здесь находится причина.

Файлы: `poster.log` — всё, уровнем INFO всегда (это аудит: кто создал заказ,
кто поменял цену); `errors.log` — только падения. `POSTER_LOG_LEVEL` в `.env`
управляет тем, что печатается в консоль, файлов он не касается.

## Куда платить: QR и реквизиты

В карточке заказа, рядом с суммами, — кнопка «Куда платить». Открывает экран,
который сотрудник разворачивает к клиенту: QR-код, получатель, номер карты и
телефон для перевода. Всё крупно — читать будут с той стороны стойки.

Сумма по умолчанию — остаток к доплате. Переключается на полную стоимость или
на свою: предоплату берут не всегда ровно половиной.

Код рисуется на месте (`segno`, чистый Python): ни сумма, ни реквизиты никуда
не уезжают, и интернет для этого не нужен.

### Два способа — выберите свой

Все реквизиты правятся в разделе «Настройки»; строки `.env` ниже — запасной
вариант для первой установки, настройки главнее.

**Ссылка на перевод — если деньги идут физлицу.** Возьмите в своём банке
ссылку («Перевести мне по ссылке», ссылка или наклейка СБП, «Мой QR» —
называется у всех по-разному) и вставьте её. Для Сбербанка:

```
POSTER_PAY_PHONE=+7 (988) 160-32-18
POSTER_PAY_LINK=https://www.sberbank.ru/ru/choise_bank?requisiteNumber={phone}&bankCode=100000000111
```

В ссылку подставляются два значения:

| Место | Чем заменяется |
|---|---|
| `{phone}` | номер из `POSTER_PAY_PHONE` в виде `79881603218` |
| `{amount}` | сумма заказа в рублях |

Номер приводится к виду, в котором его ждут банки, как бы он ни был записан в
настройках: `+7 (988) 160-32-18`, `89881603218` и `9881603218` дадут одно и то
же. Правило то же самое, по которому система узнаёт постоянного клиента по
телефону (`app/phones.py`), — номер на экране и номер в ссылке не разъедутся.
Нужен вид `+7988…` — пишите в ссылке `+{phone}`.

Места для суммы в ссылке нет — система честно скажет об этом сотруднику:
«сумму клиент вводит сам, назовите её».

> **Настоящий QR СБП умеет выпустить только банк.** Это не картинка, которую
> можно нарисовать по номеру телефона: за ней стоит зарегистрированный в НСПК
> адрес, привязанный к счёту. Мы такие не выдумываем — только показываем то,
> что банк уже выдал вам.

**Платёж по реквизитам — если деньги идут организации.** QR со строкой по
**ГОСТ Р 56042**: приложение подставит и реквизиты, и сумму.

```
POSTER_PAY_NAME=ООО Ромашка
POSTER_PAY_ACCOUNT=40702810200000000001    # 20 цифр
POSTER_PAY_BANK=Сбербанк
POSTER_PAY_BIC=044525225                   # 9 цифр
POSTER_PAY_CORR_ACCOUNT=30101810400000000225
POSTER_PAY_INN=7712345678
```

Заполнены не все пять первых — QR не показывается, а карта и телефон работают
сами по себе:

```
POSTER_PAY_CARD=2202 2002 1234 5678
POSTER_PAY_PHONE=+7 (988) 123-45-67
POSTER_PAY_NOTE=Перевод по СБП — в комментарии укажите номер заказа
```

Что показывать, система решает сама: есть ссылка — показывает её. Задать явно —
`POSTER_PAY_MODE=link` или `=gost`.

### Если банк отвечает «недопустимый номер счёта»

Скорее всего, у вас **счёт физлица** (начинается на `40817`). Формально это
счёт, но платёж по реквизитам на него часть банков в QR-сценарии не принимает.
Лечится ссылкой из предыдущего раздела — система сама подскажет это
администратору, когда увидит такой счёт.

Реквизиты проверяются при показе: длина счёта, БИК, ИНН и **контрольный ключ
счёта** (Положение ЦБ 579-П) — он считается из БИК, поэтому перепутанные между
собой счёт и банк или опечатка в одной цифре ловятся сразу. Плюс правило
«последние три цифры корсчёта совпадают с последними тремя БИК». Список «что
не так» видит только администратор — сотруднику у стойки названия переменных
из `.env` ничего не говорят.

**Проверьте на своём банке до того, как обещать сотрудникам.** Строка написана
по стандарту и читается сканером, но набор полей у банков-приёмников
различается. Если чьё-то приложение не понимает кириллицу, помогает
`POSTER_PAY_ENCODING=win1251` — код перерисуется в другой кодировке, менять
ничего не нужно.

Право — то же, что на стоимость заказа (`orders.price.view`).

## Макеты заказов

К заказу можно приложить макет — файл CorelDRAW. Он загружается через карточку
заказа и сохраняется на сервере под номером заказа: `ЗК-2026-000042.cdr`.
Папка задаётся в `.env`:

```
POSTER_DESIGNS_DIR=D:\poster\designs
```

По умолчанию — `designs/` в корне проекта.

### Откуда берётся превью

CDR начиная с версии X4 (14), включая X6 (16) — это zip-архив, внутри которого
CorelDRAW сохраняет готовую картинку-эскиз. Её и достаём: быстро и без тяжёлых
зависимостей вроде Inkscape. Для старых файлов (X3 и раньше, формат RIFF) есть
разбор чанков, плюс запасной поиск картинки прямо в байтах.

Извлечённые превью кэшируются в `designs/.previews/` и пересоздаются, когда
файл заменили.

**Превью может не быть.** CorelDRAW сохраняет эскиз, только если включена
соответствующая опция. Если её выключили, в файле картинки нет — карточка
честно скажет «превью недоступно», а сам файл останется доступен для скачивания.
Отрисовывать вектор самостоятельно система не умеет и не пытается.

Если превью не появилось, а должно было, откройте `/api/orders/{id}/design/inspect` —
ручка покажет, что именно лежит внутри файла.

### Права

    design.view     видеть превью и скачивать макет
    design.upload   загружать, заменять и удалять

## Надёжность базы

Все данные — заказы, клиенты, прайс, виды работ, профили — лежат в одном файле
`poster.db`. Это сделано намеренно: заказ ссылается на клиента, история — на
заказ, поля — на шаблон. Разнести их по разным файлам SQLite нельзя без потери
внешних ключей и атомарности: создание заказа пишет разом в три таблицы, и это
должно быть «либо всё, либо ничего».

Вместо разделения защита устроена так:

- **Журнал WAL.** Запись идёт в отдельный журнал, основной файл не рвётся на
  середине. Обрыв питания посреди записи не ломает базу — незавершённая
  операция просто откатывается при следующем открытии.
- **Проверка при старте.** Повреждённая база не даст серверу запуститься:
  лучше заметить сразу, чем через неделю, когда все бэкапы окажутся копиями
  уже битого файла.
- **Копия перед обновлением схемы.** Если при запуске нужно дописать колонки,
  сначала снимается снимок в `backups/..._before-update`.
- **Внешние ключи включены** — заказ не может сослаться на удалённого клиента.
- **Бэкапы по разделам** дают ту изоляцию, ради которой обычно и хотят
  разделять базы: `orders.json`, `clients.json` и `prices.json`
  восстанавливаются по отдельности.

Проверить состояние:

```bash
python -m scripts.check_db
```

Показывает целостность, режим журнала, битые связи, количество записей и
возраст последнего бэкапа. Стоит запускать раз в неделю и обязательно — после
некорректного выключения компьютера.

Если база повреждена, сервер откажется стартовать и подскажет команду
восстановления. Порядок: остановить сервер, `python -m scripts.restore --list`,
затем скопировать `poster.db` из нужной папки бэкапа на место рабочего файла.

Три файла рядом с базой — `poster.db`, `poster.db-wal`, `poster.db-shm` — это
норма для режима WAL. Копировать базу вручную нужно вместе с ними либо
скриптом `scripts/backup.py`, который делает это правильно.

## Статусы

`Новый → Подтверждён → В работе → Готов → Выдан`, плюс `Отменён`.

Переходы ограничены (`ALLOWED_TRANSITIONS` в `models.py`): например, из «Подтверждён»
нельзя прыгнуть сразу в «Выдан». Перетаскивание запрещённой карточки покажет ошибку,
а не сломает данные. Каждая смена статуса пишется в историю заказа.

## Виды работ и прайс

Виды работ («Плоттерная резка», «Визитки») и разделы прайса живут в базе и
настраиваются администратором в разделах «Виды работ» и «Прайс» — без правки кода.

У каждого вида свой набор полей. Поле-список берёт варианты **из раздела прайса**:
добавили материал в прайс — он появился в форме заказа, и его цена сразу
участвует в расчёте.

Формул под каждый вид работ нет — расчёт один на всех. Разницу задаёт роль поля:

| Роль | Что делает |
|---|---|
| Умножить на количество | ставка × тираж |
| Цена по ступеням тиража | от 100 шт одна цена, от 500 другая |
| Умножить на площадь | ставка × м² |
| Умножить на периметр | ставка × пог. м по краю |
| Умножить на длину | ставка × длина |
| Один раз за заказ | приладка, скрепление |
| Коэффициент | умножает всё, что стоит **выше** по списку полей |
| Ширина / Высота / Длина | измерения; единица настраивается — мм, см или м |

Порядок полей значим: коэффициент «двусторонняя ×1.8» сразу после «Формата»
удвоит печать, но не бумагу.

Стартовый каталог — семь видов работ и 13 разделов прайса — лежит в
`app/seed_catalog.py` и заливается только в **пустую** базу. Как только в
прайсе появилась хоть одна запись, сиды не срабатывают: иначе удалённый
администратором раздел возвращался бы при каждом запуске.

Залить или обновить каталог руками:

```bash
python -m scripts.seed_workshop          # дозалить недостающее
python -m scripts.seed_workshop --wipe   # стереть всё и залить заново
```

`--wipe` стирает заказы, клиентов и каталог, но не трогает профили сотрудников
и список компьютеров. Перед ним снимите бэкап — `python -m scripts.backup`.

Отдельные позиции возвращает кнопка «Восстановить недостающие» на странице
«Прайс»: она берёт данные оттуда же, что и первый запуск.

## Стоимость

Цена хранится в поле `price` и вводится руками. Кнопка «Рассчитать» в форме
обращается к `POST /api/price/estimate` и подставляет подсказку с расшифровкой —
её можно перебить своей цифрой. Уже созданные заказы не пересчитываются.

**Оплата.** Внесено меньше стоимости — «частично», столько же — «оплачен»,
больше — «переплата», лишнее видно отдельно. **«Деньги вернули клиенту»**
значит, что всё внесённое отдали обратно: галочка доступна, только если
что-то вносили. У живого заказа после возврата долг — вся стоимость, у
отменённого долга нет. После возврата система предлагает перевести заказ в
«Отменён», но не настаивает.

**Вид работ у заказа можно сменить** прямо в форме правки: строка «Вид
работ: … · сменить». Введённое переезжает — клиент, деньги, срок, и те
параметры, что совпали по ключу.

Цены правит администратор на странице «Прайс», изменения действуют сразу у всех:
расчёт читает тарифы из базы на каждый запрос, перезапускать сервер не нужно.
Каждая смена цены или единицы записывается: «менял …» в строке позиции —
кнопка, за ней история с датами. Над разделами — поиск по всему прайсу.

В конструкторе видов работ есть кнопка «Посчитать пример» — проверить настройки,
не сохраняя вид работ.

## Доска на планшете

Карточки перетаскиваются пальцем: подержать 350 мс — карточка поднимется и
поедет за пальцем, колонка под ним подсветится. Короткое касание открывает
заказ, прокрутка доски работает как обычно.

## Выпадающие списки

Все списки в интерфейсе свои, не нативные (`web/src/components/Select.tsx`):
нативный `<select>` красится только снаружи, а список из него рисует
операционная система — белый, с чужим шрифтом. Свой умеет то же, что
нативный: стрелки, Enter, Esc, набор первой буквы, группы, роли для читалки;
открывается вверх, если внизу не помещается.

## Горячие клавиши

- `/` — перейти в поиск
- `Esc` — закрыть окно

## Чего пока нет (осознанно)

- **HTTPS.** Внутри сети трафик не шифруется. Пароли и данные заказов идут
  открытым текстом — для локальной сети приемлемо, для доступа снаружи нет.
- **Файлов макетов.** Ссылку можно положить в комментарий к заказу.
- **Обновления в реальном времени.** Если за доской сидят двое, изменения второго
  подтянутся, когда вкладка снова окажется активной, — этого хватает для доски
  в цехе, но мгновенным обменом это не назовёшь. Полноценно лечится
  websocket'ом, когда станет нужно.
- **Alembic.** Схема обновляется мини-миграцией в `database.py` — списком колонок,
  которые нужно дописать. Когда изменений станет много, стоит перейти на Alembic.
